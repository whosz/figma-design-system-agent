# Export IDE Context

Turns the extracted design system into a single markdown file (`.designrules.md`)
that any AI coding assistant can consume as context via its `@file` mechanism.
Inspired by fig4ai's `.designrules` format. The output is intentionally compact
— optimized for LLM token efficiency, not human reading.

## Inputs

- `design-system/tokens/*.css` — extracted token files
- `design-system/tokens/tokens.json` — W3C token definitions with aliases
- `design-system/inventory.json` — component inventory from extract-design-system
- `design-system/target-profile.json` — tech stack for usage examples
- `library-manifest.json` (optional) — adopted library info

**Pre-flight:** If `design-system/tokens/` is empty, stop and say
"Run `extract-design-system` first — no tokens found."

## Output

`.designrules.md` in the project root.

## Format

```markdown
# Design Rules — <project name> — <date>
> Generated by figma-design-system-agent. Do not edit — regenerate via export-ide-context.

## Stack
<framework>, <language>, <CSS approach> — one line from target-profile.json

## Tokens

### Colors
| Token | Value (light) | Value (dark) |
|---|---|---|
| --color-primary-600 | #2563eb | #3b82f6 |
...

### Typography
| Token | Family | Size | Weight | Line-height |
...

### Spacing / Radius / Shadow
Compact table — one row per token.

## Components (<count> total)

### <ComponentName>
**Variants:** size: sm|md|lg · type: primary|secondary|ghost
**States:** default · hover · focus · pressed · disabled · error
**Tokens used:** --color-primary-600, --spacing-4, --radius-md
**Usage (<stack>):** `<import-or-tag-snippet>`

(repeat for every component in inventory.json)

## Hard rules (always apply)
1. Never use raw color/spacing/radius values — always bind to a token.
2. All interactive states must be implemented: hover, focus, pressed, disabled, error.
3. Component resolution order: existing library → generated components → synthesize.
4. No CSS-in-JS raw values; no Tailwind arbitrary values where a token exists.
```

## Steps

1. Read `tokens.json` — build token tables per group (colors, typography,
   spacing/radius/shadow, other). Omit empty groups. For color tokens with
   multiple modes, show all modes side-by-side.
2. Read `inventory.json` — for each component generate the compact block:
   variants, states, top-5 most-used tokens, one usage snippet per the stack
   in `target-profile.json`. Order alphabetically.
3. Append the global hard rules section (mirror rules 1–3 from AGENTS.md in
   terse actionable form).
4. Write `.designrules.md`. Report: file size, token count, component count,
   and the `@.designrules.md` invocation snippet the user can paste into
   their IDE.
5. Append work-log entry (AGENTS.md rule 9).

## Token budget guidance

Target < 6 000 tokens in the output file (fits in most IDE context windows).
If the design system is large:
- Typography composites: collapse to one row per style (not per property).
- Components: omit `tokens-used` for components with > 20 tokens (too noisy).
- Add a note at the top: "Condensed — run design-system-search for queries."

## Hard rules

1. Output is a generated view — never the place to edit tokens or rules.
   Put "Generated — do not edit" at the top.
2. Token names are copied verbatim from the extraction; never renamed.
3. If the token or inventory files are older than 7 days, warn: "Design system
   may be stale — consider running extract-design-system before exporting."
4. `.designrules.md` is regenerated in-place on each run — not versioned.
