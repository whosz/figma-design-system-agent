# Adopt Component Repo

When a real component library already exists in code, it — not Figma — is
the source of truth for implementation. Figma remains the source of truth
for *visual intent*. This skill inventories the existing library, registers
it as the agent's default, and reconfigures the other skills from
"synthesize from Figma" to "reuse from the library, flag drift".

## Inputs

- `source`: path to the library — auto-detected if omitted. Detection order:
  1. explicit user pointer (path, repo URL, npm package name)
  2. monorepo UI package (`packages/ui`, `packages/components`, workspace
     entries with "ui"/"design" in the name)
  3. in-repo `src/components/` or `components/` with consistent structure
  4. installed DS packages in `package.json` (e.g. internal `@org/ui`,
     or public ones like MUI/Chakra — confirm with the user before adopting
     a third-party library as "the" design system)
  5. Storybook config (`.storybook/`) as a strong signal + story glob as
     the component index
- `mode`: `adopt` (default) or `audit` (inventory + report only)

## Workflow

### Step 1 — Inventory the library

Build a machine-readable manifest of what exists:

- **Components**: name, import path, props/variants (from TypeScript types,
  PropTypes, or story args), states covered, framework
- **Tokens**: locate the library's own token source — CSS custom properties,
  theme object, Tailwind config, vanilla-extract/styled-system themes —
  and extract names + values
- **Docs**: Storybook stories, MDX docs, README per component

Save as `design-system/library-manifest.json` + human-readable
`design-system/docs/library-inventory.md`. The manifest is what other skills
consume; keep it regenerable (record the generation command in the file
header).

### Step 2 — Reconcile tokens

Diff library tokens against `design-system/tokens/` (and Figma variables if
a Figma file is configured):

- Tokens exist only in the library → import them into
  `design-system/tokens/` as the canonical set (the library was first; honor
  it).
- Same token name, different value between library and Figma → **conflict**:
  list all, ask the user once which side wins (typically: code wins for
  adopted repos), record the decision in the manifest.
- Never maintain two parallel token sets silently.

### Step 3 — Register precedence

Write the resolution order into `design-system/library-manifest.json`
(`"componentResolution"` field) and ensure AGENTS.md states it:

1. existing library component (this repo/package)
2. component previously generated by the agent in `design-system/components/`
3. synthesize new from Figma (`generate-component`) — last resort, and the
   new component must be generated *in the library's conventions* (framework,
   styling approach, file layout), not the agent's defaults

Downstream effects, stated explicitly in the manifest so other skills obey:
- `build-rwd-prototype` / `docs-to-prototype`: import from the library;
  inline DS-gap markup only when no library match exists
- `generate-component`: becomes "extend the library", following its
  conventions and contributing guidelines if present
- `code-to-figma`: library components map 1:1 to Figma components it creates
- `code-connect-sync`: the manifest is its component index — suggest running
  it after adoption to link the library to Figma

### Step 4 — Report

Inventory summary (counts, frameworks, token source), conflicts resolved,
precedence now in force, and gaps: Figma components with no library
counterpart (candidates for `generate-component`) and library components
with no Figma counterpart (candidates for `code-to-figma`).

## Hard rules

1. Adoption never rewrites the existing library — the agent conforms to it,
   not the reverse.
2. Third-party libraries (MUI etc.) are adopted only with explicit user
   confirmation, and the manifest records them as `external: true` (the
   agent must not edit files inside `node_modules`; extension happens via
   wrapper components in the repo).
3. One canonical token set; every conflict is surfaced, decided once, and
   recorded.
4. The manifest is the single integration point — other skills read it, they
   do not re-scan the repo ad hoc.

## Example invocations

- "We already have components in packages/ui — use them as the base"
- "/adopt-repo @acme/design-system"
- Auto-suggested when extract-design-system detects an existing components
  directory before its first run.
